# IMUリズムゲーム プロジェクト振り返り

以下に、私が担当した部分とその開発を通じて得られた知見をまとめさせていただきます。

## 担当パートと成果

私は主に**IMU（慣性計測ユニット）のデータ処理とゲームへの統合**を担当しました。

* **IMUデータ処理と信号送信**:
    * Arduino IMUモジュール（BNO085）の動作検知ロジックの実装。
    * IMUで検知した動作信号をPython側のゲームプログラムへ送信する仕組みの構築。
* **ノーツのヒット判定処理**:
    * IMUから送られたデータを基にした、ゲーム内のノーツに対する**ヒット判定ロジック**の実装。
* **システム統合**:
    * デザイナー作成の**UI**、他エンジニア担当の**グーパー判定処理**、および私が作成した**IMU処理**をメインのリズムゲームプログラムに統合。

## 開発における工夫点 

初期段階では、IMUからの入力に大きな**遅延（約0.2秒）**が発生するという致命的な問題に直面しました。これはリズムゲームとしての体験を損なうため、以下の改修を行いました。

### 1. 問題点：データ処理フローによる遅延

当初、データの送信フローは以下の通りでした。

$Arduino (IMU) \xrightarrow{\text{生データ}(x, y, z)} receiver.py \xrightarrow{\text{総加速度計算と判定}} game.py$

* `receiver.py`内で**総加速度** $Total\_acc = \sqrt{x^2+y^2+z^2}$ を計算し、しきい値（15以上）を超えた場合に`game.py`に信号を送るロジックでした。

### 2. 解決策：判定処理をArduino側へ移動

この遅延を解消するため、**総加速度の計算とヒット判定（しきい値判定）**を**Arduino側**に移動させました。

$Arduino (IMU) \xrightarrow{\text{判定済みの信号}} game.py$

この変更により、**動作検知からゲーム内でのヒット判定までの遅延を解消**することができ、リズムゲームとして成立する操作感を実現できました。

## プロジェクトを通しての反省点と今後の課題

今回の経験から、特に以下の2点について改善の必要性を痛感しました。

* **プログラム統合の難しさ**:
    * 初期のタスク分担時に、チーム開発初心者ということもあり、**プログラム間のI/O（入力・出力）の仕様**や**コネクト方法**について十分な検討を行いませんでした。
    * 結果として、個々が作成したプログラムを統合するフェーズで、多くの時間と労力を要してしまい、**開発効率が低下**しました。
* **コードの構造化**:
    * メインプログラムである`game.py`の`game_loop`関数に、**ゲームロジック**、**ノーツ生成/削除**、**IMU/グーパーの受信・ヒット判定**など、多くの処理を集中させてしまいました。
    * これにより、関数が長大になり、**可読性**や**保守性**、**デバッグの困難さ**が増しました。

### 次回の開発に向けて

次回のチーム開発では、プロジェクト開始時に**モジュール間のインターフェース（データの形式、送信タイミングなど）**を綿密に設計し、各機能を**クラスや独立した関数**として分割し、より**モジュール性の高い**コード構造を目指します。

# 1. 概要
## 本プロジェクトについて
「ジグリズム（JigRhythm）」 は、グッパーの手のジェスチャーと、貧乏ゆすりを応用した足のジグリング動作を組み合わせたリズムゲームです。
高齢者をターゲットとし、リズムゲームと身体動作を結びつけることで、認知機能と身体機能の両方を楽しみながら鍛えることを目的としています。

### gesture_processor
MediaPipe の Gesture Recognizer（手指ジェスチャー認識モデル）を用いて、
カメラ映像からリアルタイムで手のランドマーク（21点の位置）とジェスチャーを検出し、
マルチプロセス経由でゲーム側へ送信するためのプログラムです。
本スクリプトは サブプロセスで動作し、メインゲームとは独立してジェスチャー認識を行います。
検出したジェスチャーは Queue を通じてメインプロセスに送られ、ゲーム操作に利用されます。

主な機能：
- MediaPipe Gesture Recognizer モデルの読み込み
- Web カメラからのリアルタイム映像処理
- 手のランドマーク検出（最大2手）
- ジェスチャー（グー・パー・ピースなど）の分類
- 独自の「グー → パーまで連続禁止」ロジックの実装

### handtracking_util.py
MediaPipe Hands を使った「手のランドマーク処理」「手IDの追跡」「描画処理」をまとめたユーティリティモジュールです。
ゲーム本体やジェスチャー認識処理から呼び出され、手の位置情報の安定取得や可視化を担当します。

主な機能：
- 手のランドマークの取得・前処理
- 手 ID の追跡（左右の判定とは別の ID 管理）
- ランドマークの描画処理（デバッグ用）
- CSV 保存用フォーマットの構築

### main.py

このアプリケーションのエントリーポイント（起動ファイル）です。

主な役割は、「Pygameのゲーム本体」(`game.py`)と「MediaPipeのハンドトラッキング」(`gesture_processor.py`)という2つの重い処理を、別々のプロセスとして起動・管理することです。

処理の流れ：

  * `multiprocessing.Queue`を作成し、プロセス間の通信（ジェスチャー情報の受け渡し）を準備します。
  * `gesture_processor.py`をサブプロセスとして起動し、ハンドトラッキングを開始させます。
  * `game.py`をメインプロセスとして起動し、ゲームを開始します。
  * ゲームが終了すると、`finally`ブロックでサブプロセスを安全に`terminate()`（停止）させ、リソースを解放します。

使用方法：

```
rye run python -m source.main --right <右足につけたセンサのCOMポート番号> --left <左足につけたセンサのCOMポート番号>
```

このスクリプトは、ゲーム全体を起動する親プロセスとして機能します。引数は必要ありません。
